# Bring-up plan

The project should be developed as two independently testable halves and joined only after both are stable.

## Rule 1: never debug RF, transport and LCD at the same time

Each stage introduces only one unknown.

---

## Stage A — S3 LCD only

Goal: prove the S3 board can continuously drive the chosen LCD while leaving enough CPU for control work.

Checklist:

1. Flash a minimal ESP-IDF S3 project.
2. Initialize PSRAM.
3. Bring up the RGB LCD using the panel's exact timing.
4. Render a static RGB565 test pattern.
5. Render a moving test pattern for at least 30 minutes.
6. Measure frame rate and display task CPU use.
7. Confirm no PSRAM/LCD DMA errors.

Acceptance:

- stable display
- no corruption after sustained run
- framebuffer allocation succeeds reliably
- control-task test thread still meets a fixed 4 ms deadline

---

## Stage B — S3 composite decoder without C5

Goal: prove PAL/NTSC recovery from known sampled data.

Start grayscale.

Input sources, in order:

1. generated horizontal/vertical sync waveform
2. generated grayscale bars
3. recorded clean composite samples
4. recorded noisy FPV composite samples

Pipeline:

```text
8-bit samples
   -> sync threshold / edge tracking
   -> line PLL / timing estimator
   -> active-video window
   -> luma level map
   -> horizontal resample
   -> RGB565 grayscale line
   -> framebuffer
```

Do not implement PAL color before grayscale is robust under timing noise and missing lines.

Acceptance:

- locks PAL-like and NTSC-like timing independently
- cleanly reacquires after dropped sample blocks
- no unbounded buffer growth
- malformed input cannot stall RivetTX/control task

---

## Stage C — RivetTX on the same S3

Goal: prove radio-control timing remains healthy while the display and decoder are active.

Current upstream RivetTX already supports ESP32-S3 but its OpenPocket presentation path is analog OSD based. Add a digital presentation adapter rather than modifying control semantics.

Tests:

1. run RivetTX with video decoder disabled
2. run display test pattern + RivetTX
3. run synthetic CVBS decoder + RivetTX
4. inject decoder overruns and malformed blocks
5. verify RivetTX control deadlines and watchdog health

Keep propellers removed for all CRSF/RF testing.

---

## Stage D — ELRS RX-as-TX

Goal: prove the converted external module behaves like a normal CRSF TX module.

1. Verify the receiver in its original firmware first.
2. Back up its own `hardware.json`.
3. Flash the exact supported RX-as-TX target.
4. Restore the same board's hardware configuration.
5. Connect full-duplex non-inverted CRSF UART to S3.
6. Start at the lowest advertised power.
7. Bind to a separate aircraft receiver.
8. Verify channel motion, telemetry, model match and failsafe.
9. Raise to 100 mW only if the exact board advertises/supports it and thermals/power are acceptable.

Acceptance:

- no CRSF frame loss attributable to video load
- no control deadline misses
- module reconnect is handled safely
- telemetry remains live while LCD is saturated

---

## Stage E — C5 transport without RF

Goal: prove sustained C5 -> S3 bus throughput using generated bytes.

Use the protocol in [`video-link.md`](video-link.md).

Sequence:

1. 1-bit SPI at low clock with counter pattern
2. QSPI at low clock
3. raise clock stepwise
4. run PRBS pattern
5. add DMA on both sides
6. sustain 10 MS/s-equivalent payload for 10 minutes
7. attempt 13.5 MS/s-equivalent payload
8. add READY signaling and sequence counters
9. force C5 resets and verify S3 recovery

Log:

- bytes/s
- corrupted blocks
- sequence gaps
- C5 producer overrun
- S3 consumer overrun
- worst queue depth
- RivetTX deadline misses

Target margin: sustained useful throughput >= configured sample payload + 15%.

---

## Stage F — generated composite from C5

Goal: prove the whole digital-video transport independently of the RF experiment.

C5 produces a deterministic composite waveform in software/DMA:

```text
sync -> blanking -> grayscale bars -> blanking
```

S3 must display it correctly through the same transport path intended for live C5VRX samples.

This is the most important integration test before touching live RF because it isolates transport + decoder + LCD from the unknown C5 radio path.

---

## Stage G — upstream C5VRX live samples

Goal: replace the generated C5 waveform with real WBFM-demodulated FPV composite samples.

Prerequisites from upstream C5VRX:

- hardware-validated 5.8 GHz reception
- continuous complex sample production
- verified sample timing/rate
- stable WBFM discriminator
- bounded output pipeline

First live RF test:

```text
VTX: known aligned 5 GHz center channel
image: static black/white bars
power: lowest useful bench setting
C5: known supported center frequency
S3: grayscale only
ELRS: disabled
```

Only after the video is stable should ELRS be enabled and coexistence characterized.

---

## Stage H — complete handheld load test

Run simultaneously:

- live C5VRX video
- S3 PAL/NTSC decode
- RGB LCD
- RivetTX control loop
- four gimbal ADC channels
- switches/buttons
- CRSF to ELRS
- telemetry
- buzzer/warnings
- battery monitoring

Measure:

- end-to-end video latency
- video drops/minute
- control deadline jitter
- CRSF error/reconnect rate
- S3/C5 temperatures
- ELRS module temperature at each power
- battery current and runtime
- C5 reception degradation with ELRS at 100 mW

---

## Color comes last

A working grayscale FPV image is already enough to validate the architecture.

PAL/NTSC chroma decode adds:

- burst detection
- subcarrier phase/frequency recovery
- I/Q or U/V demodulation
- line-dependent PAL phase handling
- additional filtering and compute

Do not let color delay proof of the core C5 -> S3 digital receiver path.

---

## Definition of success for prototype v0

Prototype v0 is successful when:

1. the C5 receives a live analog FPV source continuously,
2. it emits a sampled composite stream without an external VRX chip,
3. the S3 decodes and displays a stable grayscale image,
4. RivetTX remains deadline-healthy at the same time,
5. the converted ELRS module controls a receiver over RF,
6. forced video faults do not interrupt the control path,
7. the complete system operates from the intended battery architecture without brownouts.

Color, DVR, polished menus and custom PCB integration are later milestones.
